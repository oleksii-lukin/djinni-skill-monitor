# 04 — Архитектура (draft)

Ориентир: Next.js + PostgreSQL (Prisma) + Telegram Bot. Локальный запуск → VPS (возможно OpenNext).
Мультитенантность закладывается с самого начала (`user_id` во всех сущностях).

## 1. Компоненты

```
┌─────────────────────────────────────────────────────────┐
│  Next.js App (веб)                                      │
│  - Дашборд: карта навыков, вакансии, профиль            │
│  - Настройки: профиль, подписки, BYOK-ключи             │
└───────────────┬─────────────────────────────────────────┘
                │ Prisma
┌───────────────▼─────────────────────────────────────────┐
│  PostgreSQL                                             │
│  jobs / skills / aggregates / profiles / users / runs   │
└───────▲──────────────────────────────────▲──────────────┘
        │ write                          │ read/write
┌───────┴──────────────────┐   ┌──────────┴───────────────┐
│  Ingestion Worker        │   │  Analysis Pipeline       │
│  - scheduler (cron/interval)  │  - skill normalization   │
│  - fetcher (rate-limited)     │  - matching engine       │
│  - deterministic parser       │  - recommendations       │
│  - RunLog                      │  - BYOK LLM client      │
└──────────────────────────┘   └──────────▲───────────────┘
                                          │ events/results
                                 ┌─────────┴────────────────┐
                                 │  Telegram Bot            │
                                 │  - notifications         │
                                 │  - commands (TBD)        │
                                 └──────────────────────────┘
```

## 2. Ingestion Worker

- **Scheduler**: встроенный (node-cron / interval в worker-процессе) — сначала локально;
  при миграции на VPS — тот же процесс в docker-compose. Vercel Cron — только если
  выберем serverless (TBD; у Vercel-варианта ограничения по времени выполнения).
- **Fetcher**: GET `/jobs/` (первые N страниц) + отдельные страницы новых вакансий;
  rate limit (пауза 1–2 с, backoff на 429/403); честный UA; уважение robots.txt.
- **Deterministic parser** (cheerio): JSON-LD + структурированные навыки + English level +
  формат/локация + статистика + зарплата. Список вакансий — основной источник (полные
  описания уже в HTML), отдельные страницы — для новых/обновлённых.
- **Raw storage**: сырые HTML (опционально, на диск/对象 storage — TBD) — для регенерации
  парсинга после изменения схемы.
- **RunLog**: каждая итерация — что скачано, сколько новых, ошибки, длительность.

## 3. Analysis Pipeline

- **Skill normalization (LLM, BYOK)**: free-text описания → таксономия скиллов
  (canonical skill + категория). Нормализация может идти пачками (batch) для экономии токенов.
- **Aggregation**: предвычисленные агрегаты (SkillMap) по направлениям: частота, required
  experience, English, форматы. Пересчёт — при новой пачке вакансий, не на каждый запрос.
- **Co-occurrence aggregation (skill gap, см. 06)**: детерминированный job — по окнам
  7/30/90 считает `share(X|S)`, `lift(X|S)`, категорийные срезы (веса must=1.0 / nice=0.5);
  кэш агрегатов (on-the-fly или предвычисление — TBD).
- **Embedding + clustering service (фаза 2, опционально, gate из 06)**: эмбеддинги сигнатур
  вакансий (title + взвешенные навыки) → HDBSCAN/K-Means → архетипы стеков; авто-лейблинг
  по топ-навыкам (LLM/TF-IDF); матчинг центроидов между запусками для стабильности.
- **Technology catalog**: каталог уровней (junior/middle/senior) по технологиям + ресурсы;
  link-out на roadmap.sh/официальные доки (iframe заблокирован `X-Frame-Options: SAMEORIGIN`;
  лицензия roadmap.sh разрешает только personal use — перепубликация запрещена; личный кэш — TBD).
- **Matching engine**: профиль ↔ вакансия → совместимость (fit / almost-fit / no). Для
  almost-fit — вычисление «быстрых для освоения» навыков (required − profile, с весом
  востребованности). Критерии — TBD.
- **BYOK LLM client**: ключи пользователей (зашифрованы в БД), выбор провайдера/модели
  (TBD: какой API), учёт расходов. Платная версия (фаза 5) — ключи провайдера + entitlement.

## 4. Telegram Bot

- **Токен общий, подписки per-user** (chat_id).
- **Фаза 4 (MVP)**: digest подходящих вакансий по расписанию + отдельные уведомления
  «почти подходит». Команды — TBD.
- **Фаза 5**: изоляция по user_id, пользовательские контакты.

## 5. Модель данных (см. 05-data-model.md)

Ключевое: `user_id` везде, где это пользовательские данные; вакансии — глобальные
(для фазы 1), сопоставление «вакансия-пользователь» — через матчинг-таблицы.

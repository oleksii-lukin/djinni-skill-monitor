# 06 — Анализ комбинаций навыков и дефицита (skill gap)

## 1. Сценарий и цель

Вход: **скилл-сет пользователя** (например `{React}` или `{C#, SQL}`) и **окно времени**
(7/30/90 дней).

Выход: система **сама находит популярные комбинации (стеки)**, включающие навыки пользователя,
ранжирует их и показывает, **чего пользователю не хватает**.

Примеры:

- **Вход**: `{React}` →
  1. React + NestJS + PostgreSQL + AWS — 18% вакансий с React;
  2. React + TypeScript + Next.js (чистый фронтенд) — 15%;
  3. React + .NET / C# — 6%;
  4. React + SEO-экспертиза — 4%;
  → для каждой комбинации: **gap = навыки комбинации минус мои**.
- **Вход**: `{C#}` или `{PHP}` → какие фронтенд-фреймворки чаще всего идут в паре
  (React/Vue/Angular) — чтобы понять, чего не хватает для fullstack-вакансий.

Также: «чистый фронтенд, но нужен гейминг-фреймворк» или «экспертиза в SEO» — такие
требования тоже должны попадать в анализ (в основном из free-text, см. §3).

## 2. Определения

| Термин | Определение |
|---|---|
| Скилл-сет пользователя | Набор навыков пользователя (`ProfileSkill`) |
| Комбинация / стек | Набор навыков, часто встречающийся вместе (например React+NestJS+PostgreSQL) |
| `share = P(X\|S)` | Доля вакансий, где есть навык X, среди вакансий, где есть навык S |
| `lift = P(X\|S) / P(X)` | Сила ассоциации: отличает «специфичное для S» (Next.js для React) от «глобально популярного» (AWS везде) |
| Веса требований | must-have = 1.0, nice-to-have = 0.5 (используются в частотах) |
| Gap | Навыки комбинации, отсутствующие в профиле пользователя |
| Окна | 7/30/90 дней — фильтр по `datePosted` в БД (у djinni нет GET-фильтра по дате) |

## 3. Детерминированная аналитика (слой 1, ядро MVP)

База: `JobSkillRequirement` (jobId, skillId, isRequired, weight) + окно + фильтр по
«интересующим» навыкам пользователя.

**Алгоритм для набора навыков пользователя S:**

1. Выбрать вакансии за окно, содержащие хотя бы один навык из S.
2. Для каждой вакансии построить взвешенный набор навыков (must=1.0, nice=0.5).
3. Условные частоты: `share(X|S)` для всех навыков X с support > порога (TBD).
4. Lift: `lift(X|S) = share(X|S) / share(X)` (baseline — частота X в том же окне глобально).
5. Категорийные срезы: X сгруппировать по категории таксономии
   (frontend-framework, backend-framework, language, database, cloud, ci-cd, auth,
   testing, domain, seo/analytics, soft/marketing). В срезе — топ-навыки с share/lift.
6. Ранжирование комбинаций: по `(share × lift × близость к пользователю)`; «близость» —
   доля уже имеющихся навыков (комбинации с большим gap внизу).
7. Для каждой комбинации: gap, avg experience, salary tier, count вакансий.

**Ограничения (честно):**

- Только то, что есть в структурированных навыках (детальных страницах вакансий); требования
  в free-text (SEO, гейминг, аналитика) — через LLM-нормализацию (слой из 04-architecture).
- Не находит архетипы вне наших категорий — сюда идёт слой 2.
- Support-пороги TBD: на малых выборках (7 дней) комбинации шумные.

## 4. ML-слой (слой 2, фаза 2, опционально)

**Задача:** эмбеддингов **сигнатуры вакансии** (title + взвешенные навыки, *не* сырое
описание) + кластеризация (HDBSCAN или K-Means) → **архетипы стеков**:

- Кластеры = повторяющиеся стеки (React+SupaBase frontend-only, React+NestJS+PostgreSQL fullstack,
  PHP+Laravel+Vue…), авто-лейблинг по топ-навыкам (LLM или TF-IDF);
- Отдельно: эмбеддинг по домену/нише (Fintech, iGaming, SEO) — где «чистый фронт + домен»
  не виден в навыках;
- Динамика: размеры кластеров по окнам (растут/уходят).

**Риски и решения:**

| Риск | Решение |
|---|---|
| Стоимость эмбеддингов | BYOK пользователя (см. ApiKey); выбор провайдера/модели TBD; локальная альтернатива — TBD |
| Нестабильность кластеров между запусками | Матчинг центроидов (косинусная близость), версионирование кластеров |
| Объяснительность | Лейблинг по топ-навыкам + LLM-обоснование; покажем share/lift кластера как раньше |
| Цена на малых данных (~6200 вакансий) | Кластеризуем навыки-сигнатуры, не тексты; объём тривиален |

**Критерий запуска (gate):** если ручной обзор 30 случайных вакансий за окно показывает
архетипы/ниши, которые категорийные срезы слоя 1 не ловят, — инвестируем в слой 2.
До этого gate — только слой 1.

## 5. Экраны

### 5.1 «Мой стек → пробелы» (overview)

Фильтры: скилл-сет (из профиля), окно (7/30/90), обязательность (must / must+nice), support-порог.

Блоки (для каждого навыка пользователя):
- **Топ комбинаций**: share, lift, count, avg experience, зарплатный тир, близость к моим
  навыкам, top gap (3–5 навыков).
- **Категорийные срезы**: что требуется поверх моего навыка (backend, cloud, CI/CD, БД,
  auth, testing, domain).
- Клик по комбинации → **Stack detail**: список вакансий (заголовок, компания, дата, зарплата,
  эксп. требования, ссылка на djinni), gap пользователя.

### 5.2 Technology page (детали технологии)

- **Свой каталог уровней** junior/middle/senior: что учить, ключевые навыки-комбинации
  (из слоя 1), частые ошибки/требования.
- **Внешние ссылки**: roadmap.sh (link-out; iframe заблокирован `X-Frame-Options: SAMEORIGIN`;
  лицензия запрещает перепубликацию — только personal-use кэш как опция, ручной релизный
  gate), официальная документация, репозитории/курсы (TBD).
- Опционально: встроенное содержимое roadmap.sh в личном режиме (см. TBD по лицензии).

## 6. Агрегаты и данные (связь с 05-data-model.md)

- `SkillCoOccurrence` / `SkillPairStat`: пары навыков (jobId → skillId), частоты,
  weights, support по окнам — основа share/lift.
- `SkillCategoryBaseline`: baseline-частоты навыков по категориям (для lift).
- `StackCombo` (кандидат): найденная комбинация (skillIds + метрики) с версионированием —
  не обязателен в MVP (считается on-the-fly), полезен для кэша/ML.
- `Technology`, `TechnologyResource`: каталог технологий и ресурсы (см. 5.2).
- `UserStack`/`SavedView`: сохранённые выборки пользователя (скилл-сет, окна, пороги).

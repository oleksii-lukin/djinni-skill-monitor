# 03 — Требования

## 1. Функциональные требования (MVP)

### Сбор и парсинг (ingestion)

- **FR-1**: Регулярный сбор вакансий с djinni.co по расписанию (шедулер; частота — TBD,
  ориентир 1–4 раза в день).
- **FR-2**: Сбор списков вакансий (`/jobs/`, с фильтрами по направлениям); первая загрузка
  — bulk (объём TBD: все страницы vs первые N).
- **FR-3**: Парсинг данных вакансии: JSON-LD, структурированные навыки с годами опыта,
  English level, формат/локация, категория, статистика, тир/реальная зарплата (если есть).
- **FR-4**: Нормализация free-text описания в таксономию скиллов (LLM-слой, BYOK).
- **FR-5**: Дедупликация по `id` вакансии; обновление изменённых; инвалидация просроченных
  (`validThrough`).
- **FR-6**: Идемпотентность: повторный сбор не создаёт дубликатов; каждая запуск сбора —
  запись в RunLog (что, сколько, ошибки).

### Карта навыков (skill map)

- **FR-7**: Агрегация скиллов по направлениям (категории/фильтрам): частота, required experience
  (среднее/распределение), English level, доли форматов работы, динамика (рост/спад) — TBD.
- **FR-8**: Карта навыков доступна как в вебе (списки/графики — UI TBD), так и в боте
  (команда «/map …»).

### Профиль пользователя

- **FR-9**: Пользователь задаёт скилл-сет (языки, фреймворки, БД, облака, инструменты),
  уровень опыта (лет), English level, желаемые направления, формат работы.
- **FR-10**: BYOK: пользователь хранит свои API-ключи моделей для анализа; ключи хранятся
  зашифрованными (TBD: режим шифрования), не попадают в логи.

### Матчинг и уведомления

- **FR-11**: Матчинг «профиль ↔ вакансия» с оценкой совместимости (подходит / почти подходит /
  не подходит). Критерии «почти» — TBD.
- **FR-12**: «Almost-fit»: для вакансии, которая почти подходит, — список конкретных навыков
  для быстрого освоения (на основе required skills минус профиль + востребованность).
- **FR-13**: Telegram-бот: подписка пользователя, регулярные оповещения о подходящих
  вакансиях (digest или поштучно — TBD), уведомления «почти подходит».
- **FR-14**: Сценарии бота (команды/меню — TBD): карта навыков, мой профиль, подписки,
  настройка приоритетов.

## 2. Функциональные требования (фаза 2, мультитенант)

- **FR-15**: Несколько пользователей: изоляция данных по `user_id` (профили, подписки, ключи).
- **FR-16**: Пользовательские контакты (TBD: что именно — Telegram ID, email, имя для откликов).
- **FR-17**: Каждый пользователь — своя подписка/чат с ботом (bot token общий, chat_id — свой).
- **FR-18**: Продуктовая модель: free (BYOK) vs платная (модели провайдера) — entitlement-логика.

## 3. Функциональные требования — анализ комбинаций и дефицита (см. [06-skill-gap-analysis.md](06-skill-gap-analysis.md))

- **FR-19**: Аналитика от скилл-сета: пользователь задаёт навыки (из профиля или вручную) —
  система строит анализ для этих навыков в окне 7/30/90 дней.
- **FR-20**: Условные частоты и lift: `share(X|S)`, `lift(X|S)` с весами must=1.0 / nice=0.5,
  support-пороги (TBD).
- **FR-21**: Категорийные срезы по таксономии (backend-framework, language, database, cloud,
  ci-cd, auth, testing, domain, seo/analytics и др.).
- **FR-22**: Ранжирование комбинаций (share × lift × близость к профилю) и **gap** пользователя;
  список стеков генерируется системой по популярности/востребованности.
- **FR-23**: Drill-down: список вакансий выбранной комбинации/навыка (заголовок, компания,
  дата, зарплата, ссылка на djinni).
- **FR-24**: Technology page: свой каталог уровней (junior/middle/senior) + внешние ссылки
  (roadmap.sh link-out, официальная документация).
- **FR-25** (опционально, фаза 2): ML-слой — эмбеддинги сигнатур вакансий + кластеризация
  (HDBSCAN/K-Means) архетипов стеков; запуск по критерию из 06.

## 4. Нефункциональные требования

- **NFR-1 (вежливость)**: rate limiting (паузы между запросами), соблюдение robots.txt,
  backoff при 429/403, ротация UA (TBD).
- **NFR-2 (надёжность)**: перезапуск с места остановки; сбор и парсинг не теряют данные
  при падении; очередь/повторы на ошибках (TBD).
- **NFR-3 (производительность)**: агрегаты по карте навыков — без полных пересчётов на каждом
  запросе (кэш/предвычисленные таблицы — TBD).
- **NFR-4 (секурность)**: BYOK-ключи не в репозитории и не в логах; шифрование в БД;
  изоляция данных мультитенантных пользователей.
- **NFR-5 (переносимость)**: сначала локальный запуск (pm2/docker), миграция на VPS без
  переписывания (Next.js + PostgreSQL + Prisma, возможен OpenNext).
- **NFR-6 (прозрачность)**: RunLog: сколько страниц, сколько новых вакансий, сколько
  обработано LLM, ошибки.
- **NFR-7 (стоимость анализа)**: учитывать расход BYOK-токенов; агрегаты считать дешевле,
  чем матчинг каждой вакансии на каждой итерации (TBD: стратегия).

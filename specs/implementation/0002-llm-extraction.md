# 0002 — LLM-слой извлечения навыков (4-й слой)

- **Status**: accepted
- **Дата**: 2026-10-24
- **Ветка/этап**: F1+ (качество данных перед аналитикой/кластеризацией)

## Context

Факт: из 246 кэшированных detail-страниц **129 (52%) разбираются с 0 навыками**, и у всех
129 в разметке djinni просто **нет блока «Навыки»** — не сбой парсера. Требования таких
вакансий (BA, media buyer, маркетинг и др.) живут только в свободном тексте описания
(1600–3400 символов). Три детерминированных слоя (structured/extra/keyword) для них дают
0, поэтому для половины рынка аналитика сейчас слепа: `jobPostings` без навыков — 598 из 750
активных, кластеризовать/считать доли не на чем.

Требование пользователя: извлекать навыки из текста с помощью LLM/лёгких моделей уже сейчас,
а не в «фазе 2». Ограничения: LLM-вызовы платные → нужен гейт; raw HTML лежит на диске →
проход возможен офлайн, без доскрейпа.

## Decision

**4-й слой `LLM_DESCRIPTION`** с гейтом: вызывается только если после трёх детерминированных
слоёв навыков `< LLM_EXTRACT_THRESHOLD` (default 1). Порядок приоритета источников:
`structured > extra > keyword > llm` — LLM заполняет пробелы и не перетирает словарные/структурные находки.

**Обновлено 2026-10-24 (после пилота)**: локальная LM Studio + `qwen/qwen3-4b-thinking-2507`
отклонена — reasoning съедает генерацию (пустые `content`, «No output generated» на 2 попытках
подряд), при том что сырой запрос к той же модели вручную давал валидный результат. Слой
реализован и протестирован инфраструктурно (гейт/лимиты/ретраи/схема), но оставлен
**выключенным** (`LLM_ENABLED=0`) до выбора нормальной модели (Zen `deepseek-v4-flash-free`
или др.). Дополнительно введён `LLM_STRUCTURED_OUTPUTS` (json_schema vs json_object):
дефолт json_schema работает с LM Studio, часть шлюзов требует json_object.

| Параметр | Решение | Обоснование |
|---|---|---|
| Провайдер | **Vercel AI SDK** (`ai` + `@ai-sdk/openai-compatible` + `zod`), один OpenAI-совместимый фасад | Переключение бэкенда одним env: OpenCode Zen, OpenRouter, OpenAI, Gemini-compat, **LM Studio** (localhost:1234) |
| API-ключ | Новый ключ под API: OpenCode Zen `https://opencode.ai/zen/v1` (opencode.ai/auth), бесплатные модели (`deepseek-v4-flash-free` и др.) | Сервер OpenCode как LLM-прокси не используется — его HTTP API агентский (сессии/промпты, без `/v1/chat/completions`); Zen — официальный OpenAI-совместимый шлюз той же команды |
| Структурированный вывод | `generateText` + `Output.object({schema: zod})` | Валидация на стороне SDK; мусорный JSON = ретрай, а не запись в БД |
| Промпт | Инструкция EN + canonical-имена словаря (162) + заголовок + описание (усечение `LLM_MAX_DESC_CHARS=8000`); `temperature=0` | Детерминизм; словарь — единственный источник истины для имён |
| Персист | `resolveSkill()` → canonical через словарь, неизвестное → `Skill(isCanonical=false)` + отчёт нераспознанных; идемпотентная замена только `source=LLM_DESCRIPTION` | Тот же механизм курации словаря, что у детерминированных слоёв; re-run безопасен |
| Гейт/экономия | `LLM_EXTRACT_THRESHOLD=1` (только «нулевики»), `--limit N` (лимит платных вызовов в прогоне), `LLM_CONCURRENCY=3` | 129 из 246 кэш-вакансий требуют LLM; ~1–2k токенов/вакансия |
| Точка входа | `pnpm extract:llm [-- --limit N] [--job ID]` — офлайн по `RAW_STORE`, RunType `EXTRACT_LLM` | Сначала валидация на кэше; интеграция в scrape-пайплайн — отдельным шагом после проверки качества |

**Схема БД**: enum `SkillSource` += `LLM_DESCRIPTION`, enum `RunType` += `EXTRACT_LLM`
(миграция `20261024185916_llm_extraction`).

## Consequences / Trade-offs

- **Стоимость и лимиты**: каждый вызов — платный запрос (на бесплатной модели Zen — нет);
  `--limit` и гейт ограничивают расход; итог с токенами печатается в конце прогона.
- **Качество зависит от модели**: free-модели могут хуже различать must/nice в UA/RU-тексте —
  валидация вручную на 5–10 образцах (`--job`) до полного прогона; `temperature=0` + ретраи
  снижают разброс.
- **Неизвестные словарю имена умножатся** после прогона — ожидаемо: отчёт нераспознанных
  становится основным источником кандидатов для курации `dictionary.ts`.
- **Слой в scrape не встроен** — `pnpm scrape` работает как раньше (детерминированные 3 слоя);
  LLM-проход отдельной командой до решения о встраивании.
- Детерминированные слои по-прежнему первичны: LLM дёргается только при < порога —
  пайплайн воспроизводим без ключа (`LLM_ENABLED=0` → команда отвечает подсказкой).

## Роадмап кластеризации (зафиксировано, БЕЗ реализации)

Обсуждение 2026-10-24 о «лёгких» навыках (Git) и разнесении их на тяжёлые/лёгкие:

- **Две оси**: информационная ценность (универсальность — вычисляется из данных:
  lift/покрытие по кластерам) и цена освоения (только ручная аннотация словаря).
  Кластеризация решает первую, но не вторую.
- **Архитектура**: модель рынка строится **офлайн по накопленному корпусу**
  (co-occurrence граф + сообщества/Louvain или NMF), а малые окна (неделя, стек-фильтр,
  30 вакансий) лишь **проецируются** на готовую модель — кластеризация не требует
  большого объёма в самом окне.
- **Предпосылки**: покрытие навыков (этот ADR — первый шаг) и объём корпуса (~1–2k+ вакансий).
  Прототип — офлайн на CSV-снапшотах (pandas/networkx), валидация — читаемость кластеров.
- Параллельно, дешёвые шаги: категорийный вес пробелов в `stats` (CONCEPT/DOMAIN/OTHER —
  отдельным фоновым блоком) и ручной флаг цены освоения в словаре.

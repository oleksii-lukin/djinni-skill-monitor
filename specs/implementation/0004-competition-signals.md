# 0004 — Сигналы конкуренции: сбор, хранение, сравнение с рынком

- **Status**: accepted
- **Дата**: 2026-11-01
- **Ветка/этап**: F1+ (данные о конкуренции; без профиля пользователя)

## Context

Скилл-сет вакансии отвечает на «подхожу ли я», но не на «стоит ли подаваться»: сколько людей
уже откликнулось, как активен рекрутер, какова доля вакансий с большим откликом. Эти данные
на djinni есть, но проект их не собирал.

Найдено в исследовании 2026-11-01 (specs/02 §3.1):

1. **Detail-страница** в `#job-publication-info` отдаёт разбивку `За 30 днів` (просмотры ·
   отклики), `Активність рекрутера` (4 значения) и `Відповідали …` с **точным timestamp в
   tooltip** (`16:29 14.10.2026`, Europe/Kyiv). Парсер брал только all-time пару — три
   сигнала терялись.
2. **Скрытая статистика кандидатов**: кнопка «Огляд кандидатів» вызывает
   `GET /api/jobs/<id>/?apply_stats` и получает публичный JSON **без авторизации** —
   `total_applicants` плюс распределения по опыту, English, зарплатным ожиданиям и топ-навыки
   откликнувшихся. Это единственный источник абсолютного числа конкурентов.

Требования: собрать сигналы; хранить без привязки к пользователю (рыночное подмножество,
ADR 0001); сравнивать вакансии с рынком; не перегружать djinni.

Пользовательское решение этапа: **только данные, без профиля и матчинга** — «абсолютные
значения по любой вакансии и сравнение со средними откликами по другим вакансиям».

## Decision

| Параметр | Решение | Обоснование |
|---|---|---|
| Сбор `apply_stats` | Отдельная команда `pnpm competition`, **он-деманд для шортлиста** (файльтры `--skills/--category/--window`, `--job`), не в `scrape` | Скрейп и так делает 1 запрос на detail; удвоение запросов ради данных, нужных только для части вакансий, — лишняя нагрузка на djinni |
| TTL снапшота | `COMPETITION_TTL_HOURS` = 24 ч; `--ttl-hours`, `--force`, `--no-fetch`, `--dry-run` | Конкуренция меняется за дни, а не за часы; 24 ч — компромисс между свежестью и нагрузкой |
| Хранение | Одна строка `JobApplicantStats` на вакансию (jobId = PK), **только последний снапшот**; JSON-массивы + `rawJson` как есть | История/тренды — отдельный этап; `rawJson` позволяет перепарсить после правок парсера (принцип сырых данных, ADR 0001) |
| Разбор | zod-схема с `.default([])` для массивов, `null` при несовпадении — вакансия пропускается, прогон не падает | API публичный, но не документирован и может измениться |
| Профиль откликнувшихся | Нормализация меток djinni в `metrics.ts` (бакеты опыта, ранги English, вилки зарплат); доли — `count / сумма(count)` | `percent` у djinni — нормировка на максимум, не доля; счёт по нему дал бы 100% для каждого бакета-лидера |
| Detail-сигналы | Расширить `parseDetailPage` + перепарсинг кэша `pnpm parse` | 1058 закэшированных detail-страниц обновляются **без сети** |
| Timestamp ответа | `parseDjinniDateTime` с `Intl.DateTimeFormat` + `timeZone: Europe/Kyiv` (двухпроходный, на границе перевода времени) | Относительная подпись («вчора») живёт только в HTML; абсолютная дата из tooltip стабильна и переживает перепарсинг |
| Рынок (baseline) | Все активные вакансии **с** снапшотом, не только выборка; перцентили при `n ≥ 10`, иначе `no-baseline` и без score | Сравнение с произвольно отобранным шортлистом врёт; малая выборка не даёт перцентилей |
| «Актуальность» | `OR: datePosted >= since \| updatedAtDjinni >= since` | Вакансии поднимаются обновлением («Оновлено …») при старой дате публикации — окно только по `datePosted` их теряет |
| Свежесть vs возраст | `ageDays` (от публикации) — для lifetime-темпа; `lastActivityAt = max(datePosted, updatedAtDjinni)` — для флагов `fresh`/`stale-listing` и колонки «Обновлена» | Смешение дало бы «216 дн. + fresh» — противоречие в таблице |
| Темп откликов | `replies30d/30` при наличии, иначе `totalApplicants/ageDays` | 30-дневный темп не размазывает старые отклики; молодые вакансии разбивки не имеют |
| RunLog | Новый `RunType.SCRAPE_COMPETITION` и счётчик `jobsStatsFetched` | Счётчики `pagesFetched`/`jobsRefetched` семантически про HTML, не про JSON-снапшоты |
| Флаги рекрутера | Взаимоисключение: `responsive-recruiter` (HIGH/VERY_HIGH или ответ ≤ 7 дней) приоритетнее `silent-recruiter` | «Низкая активность + ответил 3 дня назад» — это живой рекрутер, а не два противоречивых флага |
| Профиль/матчинг | **Не реализуются** | Решение этапа: рыночные данные не привязываются к пользователю (ADR 0001 сохраняется) |

## Consequences / Trade-offs

- **Запросов +1 на шортлиста**: `--limit 50` ≈ 4–5 мин при паузе 3–8 с. `--dry-run` печатает,
  сколько запросов было бы. Baseline на 100 вакансий собирается прогоном
  `--window 90 --limit 100 --export`.
- **Нет истории**: повторный добор перезаписывает снапшот — тренд конкуренции недоступен;
  для него нужна отдельная таблица периодических снимков (вне скоупа).
- **`total_applicants` ≠ `repliesCount`**: разное время снимка/перевыпуск вакансии; оба
  значения хранятся, в выводе показываются отдельно.
- **404 на `apply_stats` не помечает вакансию EXPIRED** — семантика эндпоинта неизвестна;
  такие вакансии повторно опрашиваются каждый прогон (дешёвый отказ, но шум в логе).
- **Baseline растёт вместе с данными**: первые прогоны показывают только абсолютные значения;
  документировано в выводе (`no-baseline` + подсказка команды добра).
- **Глобальный baseline** сравнивает разные ниши (QA vs Lead) — осознанный компромисс на
  старте; срез по категории — следующий шаг, если глобальный перцентиль окажется бесполезным.
- **Профиль по-прежнему вне БД** — сигналы конкуренции не создают соблазна смешать
  рыночные и пользовательские данные.

## Проверка

- `pnpm typecheck` — чисто.
- `pnpm check:fixtures` — офлайн: разбор detail-сигналов на 4 семплах (включая случай без
  30-дневной разбивки), разбор 3 реальных JSON `apply_stats`, нормализаторы меток.
- Ручной прогон: `--job 834543` (1 запрос), `--window 30 --limit 15 --export` (15 запросов,
  таблица + JSON/CSV), `--skills React,TypeScript --limit 8 --no-fetch`.
- `pnpm parse` по кэшу: 1058 вакансий, 237 с `views30d`, 333 с активностью, 433 с датой ответа —
  без единого сетевого запроса.
